## 2026-11-18 — Detect a unit that no longer matches the inventory, and offer to update it (planned)
- Decision: at each refresh, read-only, the unit a process should have is compared with the file on the Pi (units with our marker only); a difference shows “Unit out of date” in Next step. “Install app…” that changes `run`, `env_files` or `processes` on an app with an installed unit adds a ticked “Update the unit too” to its confirmation. Writing a unit never restarts the process.
- Why: the developer changed the run command with “Install app…” and it had no effect until “Install unit…” was run again; nothing showed the gap and the row said Ready.
- Alternatives rejected: always rewriting the unit inside “Install app…” without asking (hides a system file change); leaving the two actions separate with no hint (the current behaviour); restarting after the rewrite (restarts are decided by `on_update`).
- Consequences: built 2026-11-18 (WORKFLOW §6b item 7), detection and the ticked “Also rewrite the unit” box in Install app (GUI and `--update-unit/--keep-unit`); the box is offered only when `run`, `path` or env files changed for a known app with a unit of ours, and the rewrite never restarts. The comparison reads three fields of the unit file (run command, env files, working folder) instead of re-rendering the whole text: the rest depends on the Pi (Node's folder moves with nvm) and would flag false drift.

## 2026-11-18 — Several processes per app, each with an update rule (planned)
- Decision: an app's `apps.yaml` entry gets an optional `processes:` list `{name, run, on_update}`, each its own unit `<app>-<name>.service` sharing the working copy and env files. `on_update` is `restart` (default, today's behaviour), `keep` (an update never restarts it; it runs the old code until restarted by hand) or `ask` (a tick box in the Update confirmation). An app with one `run` stays valid and is the process `main`. The update plan lists what happens to each process; the table shows one row per process, with “old code” for a kept process started before the last build.
- Why: the app Vocalog runs a collector and a web server from one repository, and the collector must not be restarted on every update. Asked by the developer; also the open request in that app's `docs/RASPI-MANAGER-REQUESTS.md`.
- Alternatives rejected: a tick box per update with no stored rule (easy to forget, restarts by mistake); two apps from one repository (two clones to keep at the same commit); a process manager inside the app.
- Consequences: not implemented yet; WORKFLOW.md, SPEC.md and ARCHITECTURE.md are written first. Risks to cover: a rollback or build replaces files under a kept process; a schema change under a kept process that shares a database.

## 2026-11-17 — Move an app and its data to another Pi
- Decision: **App → Move to another device…** / `host move-app SOURCE APP TARGET` stops the app on SOURCE, copies each `requires: folder` (tar) and each env file to TARGET through this PC, compares SHA-256 of every file, starts the unit on TARGET, then disables SOURCE's unit. TARGET must already have the app set up (inventory, working copy at the same revision, unit, not running): moving carries only what is not in git, it does not clone or build. The env file is copied (read on SOURCE, written `chmod 600` on TARGET, never shown or kept on the PC). SOURCE data is kept until “Remove app…”. Transfer is always relayed by the PC: `ByteTransport.run_bytes` (script as the remote command, data on stdin), data held in memory, capped at 512 MB.
- Why: an append-only SQLite journal that cannot be rebuilt (an app whose data is such a journal): a copy made while the app runs, or two instances at once, loses or duplicates events. Asked by the developer; the three open questions of the request (env file, relay, retention) were answered by them.
- Alternatives rejected: Pi-to-Pi copy (needs an ssh key from one Pi to the other, against “nothing extra on the Pi”); asking to retype the env (omissions before a start); setting TARGET up inside the move (the deploy key needs a manual GitHub step); streaming to a temp file on the PC (more code, secrets and data on disk for no gain at this size).
- Consequences: failure before the start restarts the source and empties the folders just written on TARGET; a target that does not start is stopped. Not done: app-provided check command, route and inventory follow-up, data above 512 MB (copy by hand with the app stopped).

## 2026-11-17 — Manage deploy keys from a window, GitHub side stays manual
- Decision: **Pi → Manage deploy keys…** (and `host deploy-keys|deploy-key-rotate|deploy-key-rm`) lists the keys raspi-manager made on a Pi and offers check, copy, rotate and delete. The key is found by file name (`raspi_deploy_<name>`) and by the marker in `~/.ssh/config`; the repository comes from the inventory app of the same name. Rotation = delete the key files, then the usual idempotent creation script. Deletion reuses the removal script's key lines (`core/remove.key_removal_lines`), so both paths stay identical.
- Why: the key was only visible once, at creation; there was no way to find its public key again, spot orphans, or replace a leaked one.
- Alternatives rejected: calling the GitHub API to add/remove deploy keys (needs a token with repo admin rights stored on the PC, a new secret for little gain at 2–5 Pis); storing the repository next to the key on the Pi (a second source of truth).
- Consequences: after a rotation the old key stops working at once and updates of that app fail until the new key is added on GitHub (the confirmation says so). Old keys on GitHub are deleted by hand.

## 2026-11-16 — Several routes per app, checked on every status; “Reset from template…”
- Decision: an app's `apps.yaml` entry gets an optional `routes:` list of `{hostname, port, check}` (`check`: URL path, default `/`, letters digits `. _ ~ / -` only, no query). “Set up route…” / `route add [--check PATH]` is run once per hostname; every success is recorded there (`services/declare.record_route`; a Pi without `apps.yaml` records nothing and says so). All routes of an app share its one tunnel `raspi-manager-<pi>--<app>`; only the first creates the connector. The same hostname twice in one app is refused when read; a hostname or port shared with another app is a warning in the plan. Every status script runs `curl -s -o /dev/null -m 3 -w %{http_code}` on `http://127.0.0.1:<port><check>` for each route and keeps only the code (any code below 500 counts as answering); a down route turns the running app's Next step into “Route not answering” with “main up, share down” style detail. Also: the Environment editor gets **Reset from template…** (replaces the editor's variables by `.env.example`'s, nothing pushed).
- Why: Silent Fill needs two public hostnames on two ports (app and share pages) and a per-route status that names the cause when one port is taken. Asked by the developer; requests came from the app's own `docs/RASPI-MANAGER-REQUESTS.md`.
- Alternatives rejected: deriving routes from Cloudflare on every refresh (token and API call every 10 s); one hostname per app plus free-form extra tunnels; a health URL checked through the public hostname (goes through Access and the internet).
- Consequences: a route already set up in Cloudflare but not recorded is recorded only by running Set up route… again with a change; removing a route in the Cloudflare window does not yet remove it from the inventory. Not done from the same request: secret flag per key, required-keys check and last log lines after a failed start, bind-address warning, per-app deploy checklist, Access per hostname.

## 2026-11-16 — Set up route replaces the token of a running connector whose tunnel is gone
- Decision: `plan_app_route` no longer treats a running connector unit as proof that routing works. When the unit is active it asks Cloudflare: if the tunnel has to be created (so the running connector belongs to a deleted tunnel) or its status is not healthy/degraded, the plan includes the Pi part again (fetch the new token, rewrite `/etc/cloudflared/raspi-tunnel-<name>.env`, `systemctl restart`), the steps say “Replace the token…” and the confirmation gives the reason. The install script now ends with `enable` and `restart` instead of `enable --now`, so a unit already running picks up the new token. A Cloudflare lookup error keeps the old behaviour (nothing replaced).

- Alternatives rejected: always reinstalling the connector (restarts a working tunnel on every run); reading the journal for “Tunnel not found” (fragile, needs a root-free journal read); asking the developer to stop the unit by hand.
- Consequences: Set up route… on an app whose tunnel is healthy still changes nothing on the Pi; the repair costs one extra Cloudflare read per run; the 32-bit `raspi` connector problem (“control stream encountered a failure”, probably QUIC/IPv6) is a different cause and is not addressed here.

## 2026-11-15 — A second install on a Pi is refused, and apt waits for its lock
- Decision: the GUI keeps a per-Pi flag (`gui/busy.py`) while an install runs (provision, Node, tools): a second click shows “a change is already running on <pi>” and runs nothing. Every `apt-get` in generated scripts carries `-o DPkg::Lock::Timeout=600`, so an apt run started elsewhere (a first install still unpacking, the daily apt timers) is waited for, up to ten minutes, instead of failing.
- Why: the first real “Install tools” on `raspi-v` was clicked twice; the second failed with “Could not get lock /var/lib/dpkg/lock-frontend … held by process … (apt-get)” while the first was still installing ffmpeg (checked read-only: `apt-get install -y ffmpeg` running 43 s, `dpkg` unpacking). Installing hundreds of packages on a Pi takes minutes, so a double click is natural.
- Alternatives rejected: killing the other apt process (could corrupt dpkg); a lock file on the Pi (a second source of truth, stale after a crash); disabling the button during the run only (does not cover the CLI or another window).
- Consequences: the flag lives in the GUI process only (two windows or the CLI at once rely on apt's own wait); only installs are covered, not Start/Stop.

## 2026-11-15 — ffmpeg through apt, yt-dlp from the official release (checksum + a test run before replacing)
- Decision: **Pi → Install tools…** / `host install-tools` install ffmpeg with apt (a fixed whitelist: `ffmpeg`, plus `unzip` when the 32-bit bundle needs it) and yt-dlp from the latest official GitHub release (checked online 2026-11-15: 2026.10.26; Debian 13's package is 2025.04.30, trixie-backports has 2026.10.26 but needs another repository). The file depends on `uname -m`: `yt-dlp_linux` (x86_64) and `yt-dlp_linux_aarch64` are single executables, `yt-dlp_linux_armv7l.zip` is a PyInstaller folder unpacked in `/opt/yt-dlp` with a link in `/usr/local/bin`. The SHA-256 comes from the release's `SHA2-256SUMS` (read by the PC), is checked on the Pi, and the download is run once (`--version`) before it replaces anything; a build that does not run on that Pi (for example a glibc too old for the 32-bit bundle) leaves the system as it was.
- Why: yt-dlp stops working when it lags behind the sites it reads, so a six-month-old distribution package is not a real option; `/usr/local/bin` is in the PATH of the units raspi writes; the test run protects a working yt-dlp from being replaced by one that cannot start.
- Alternatives rejected: Debian's package (too old); backports (adds a repository to every Pi); pipx (needs a recent Python, the 32-bit Pi has 3.9); a `curl | sh` installer (nothing to check).
- Consequences: only the checksum is verified, not the GPG signature (`SHA2-256SUMS.sig`), same trust level as cloudflared; the binary is root-owned, so `yt-dlp -U` cannot update itself and updating means installing again (the picker shows when a newer release exists); the 32-bit bundle has not been run on `raspi` yet.

## 2026-11-15 — Remove app: separate ticked items, Pi first and list last, data and Cloudflare never touched
- Decision: “Remove app…” / `host remove-app` offer six items: list entry and unit (ticked at first, as chosen by the developer), working copy, deploy key + alias, env files on the Pi, local env copies (unticked). Guards: the unit only if it carries our marker; the working copy only if it is a git working copy under the home folder and holds no `requires:` path (re-checked inside the script: `case "$d" in "$HOME"/?*`, `[ -d "$d/.git" ]`); env files only under home; the ssh config block only when it still has the exact shape raspi wrote. The script is shown and follows the ticks; the app name is typed to confirm. The Pi side runs first and the list entry is removed last, so a failure leaves the app listed and the removal can be retried. Never touched: `requires:` folders, anything outside home, the Cloudflare route, tunnel and connector (they have their own window and DNS to think about).
- Why: removal is the only operation that deletes things on the Pi; independence of the items and defaults that keep the code, the key and the secrets make a stray click cheap, and the script runs against a real throw-away home in the tests, not only against strings.
- Alternatives rejected: everything ticked (one click from losing the .env); forgetting the entry only (leaves unit, folder and key to clean by hand); also removing the Cloudflare route (touches an account and DNS, needs its own preview).
- Consequences: an app declared in hosts.yaml (not on the Pi) is not removable here; a unit not made by raspi-manager stays; removing the route and the connector remains a separate step in the Cloudflare window.

## 2026-11-15 — App prerequisites: declared, checked on every status, reported, never created, never blocking
- Decision: `requires:` in an app's `apps.yaml` entry lists `{kind, path}` with kind `folder`, `file` or `mount` (`mountpoint -q`), absolute path without `..`, no duplicates. The status script tests each one read-only and the result travels in `AppStatus.requires_present`. A missing prerequisite is named in the “Next step” column (“Prerequisite missing”, before Start), in the wizard's start step, and in a “Start anyway?” confirmation of the Start action. It never blocks a start.
- Why: Notes App refuses to start without its data folder marker so that nothing is written to the SD card when the USB disk is not mounted; the tool should say so before the start rather than after in the logs. Creating the folder would defeat that protection, hence never created. Not blocking: the developer knows better than a path test (a mount may be elsewhere, a marker may be renamed).
- Alternatives rejected: letting raspi create the folder (writes on the SD card); blocking the start (rigid); an app-specific check script (arbitrary code to run and review).
- Consequences: one extra read-only line per prerequisite per refresh; a prerequisite that is not satisfied shows only after the next refresh (10 s); “mount” needs `mountpoint` on the Pi (util-linux, present on Raspberry Pi OS).

## 2026-11-15 — Update: a detached checkout of one exact commit, rollback to `previous`/`built`
- Decision: “Update…” / `host update|rollback` check out one full commit hash with `git checkout --detach` (for a branch tip, a tag, a sha and a rollback alike), rebuild, and restart the unit only if it was running. Refuses uncommitted changes to tracked files (`git status --untracked-files=no`) and commits not on any remote (`git rev-list HEAD --not --remotes`). `apps.yaml` gets `previous: <rev>` next to `built`; a successful update sets `built` to the new revision and `previous` to the old one, a rollback returns to `previous` (or to `built` after a failed update) and clears it. The plan runs `git fetch` (writes only remote-tracking refs in `.git`) so that incoming commits can be listed; this refines workflow decision 2, which said “fast-forward”.
- Why: a fast-forward merge cannot go backwards and leaves a branch that moves under the working copy; one detached commit is the same operation in every case, and what runs is always one named commit. The two refusals protect work done by hand on the Pi.
- Alternatives rejected: `git pull` / merge (history-dependent, can conflict); `git reset --hard` (destroys local work); `releases/<sha>` folders (more disk and structure, not needed yet).
- Consequences: after the first update the working copy is on a detached HEAD (harmless, `git status` stays usable); a failed build leaves the new code checked out but not recorded, so “Next step” asks for a build and a rollback is available; an app with build outputs tracked in git would be refused as dirty.

## 2026-11-15 — Env files start from the project's template; secrets and placeholders start empty
- Decision: the Environment declaration finds templates (`.env.example`, `.sample`, `.template`, `.dist`) as well as real files, including for an app without a declared path (`~/apps/<app>`), and offers to create the missing `.env` beside a template. When the file is absent on the Pi and nothing is saved locally, the editor starts from the template: defaults written by the project are kept, names that look secret and placeholder values start empty, and the empty variables are counted and named (never their values) in the editor and in the push confirmation. This refines decision 6 of the workflow (names only) after the developer chose “names + non-secret defaults”.
- Why: for Notes App the old dialog skipped templates and, without a declared path, did not scan at all, so nothing was proposed and the editor opened empty. Defaults such as `PORT` or `COOKIE_SECURE` are the project's own and save typing; guessing which names are secret from their words is conservative (a false “empty” costs a keystroke, a false default could leak a placeholder).
- Alternatives rejected: names only, all values empty (more typing, same risk); copying the template verbatim (pushes example values such as `change-me` unnoticed).
- Consequences: a variable with a harmless-looking name but a sensitive example value would be kept; the push confirmation lists empty ones but does not block; the pre-fill is not yet part of a wizard.

## 2026-11-15 — Scripts are read whole by the Pi before they run; a missing unit is its own state
- Decision: the transport sends the script on stdin and runs `sh -c 'eval "$(cat)"'` on the Pi, instead of `sh -s`. `cat` reads all of stdin first, so a command inside the script that reads stdin (a build tool, an installer) sees end-of-file and cannot swallow the following lines. The script stays in memory (no temporary file, so secrets such as a tunnel token never touch the Pi's disk through this path). A `LoadState=not-found` unit is shown as state `no-unit` (“– no unit”), Start is disabled for it with an explanation, and tests run every generated script through `sh -n` and reject bashisms.
- Why: with `sh -s` the shell reads its script from the same stdin the commands inherit, so truncation would be silent; the real build of an app is exactly the kind of command that may read stdin. A start that fails with “Unit not found” was a bug report waiting to happen.
- Alternatives rejected: `< /dev/null` on each command (easy to forget on the next one); a temporary file on the Pi (secrets on disk); `sh -c "<script>"` as an argument (Windows command-line length limit).
- Consequences: the remote command must keep the exact quoting (tested); `exit` inside a script ends the whole evaluation as before.

## 2026-11-15 — App units: `EnvironmentFile=` points at the app's declared env files; enabled, not started
- Decision: `install-unit` writes `/etc/systemd/system/<app>.service` (marker `# managed by raspi-manager`) with `User=<login user>`, `WorkingDirectory=<working copy>`, `Environment=PATH=<nvm node bin>:/usr/local/bin:/usr/bin:/bin`, one `EnvironmentFile=<path>` per env file declared in the inventory (the files the Environment… editor already pushes), `ExecStart=/bin/sh -c "exec <run>"` with `%`, `$`, `\` and `"` escaped for systemd, `Restart=on-failure`. It enables the unit but does not start it. A unit file without our marker is never overwritten.
- Why: one source for variables (the file the developer already edits, nothing to change for adopted apps); `sh -c exec` lets `run` be `npm start` without an absolute path while PATH carries the nvm Node; not starting leaves time to push the environment and prepare data folders (Notes App refuses to start without its data directory marker).
- Alternatives rejected: `/etc/raspi/<app>.env` owned by root (second push path with sudo, not supported by the editor; was the ARCHITECTURE sketch, now superseded); no EnvironmentFile (raspi would not control what the app receives); starting right after enabling (fails when the env file or data folder is not ready).
- Consequences: the unit fails to start if a declared env file is missing (the plan warns); a run command with its own quoting goes through sh, so keep it one line; after changing `run`, run `install-unit` again to replace the unit.

## 2026-11-15 — Clone and build: plain working copy in `~/apps/<app>`, existing copy untouched, app recorded after a successful build
- Decision: `install-app` clones into `~/apps/<app>` (or the app's `path`) with a plain `git clone` of the default branch through the deploy-key alias, runs `build` in it, and only then adds the entry to the Pi's `apps.yaml` (unit name `<app>.service`). A folder that is already a git working copy is kept as is (no fetch, pull or checkout); a non-empty folder that is not one is refused. `build` and `run` are one-line shell commands from the developer's own `apps.yaml`: validated (no control characters, 500 characters), shown in full before anything runs, never assembled from other values.
- Why: the `releases/<sha>` layout and version switching belong to the deploy step (F3), so install stays a safe first step that can be repeated; recording after the build means a failed build leaves no half-declared app and the command can simply be run again. Notes App (first real app) is built with `npm ci && npm run build` and started with `npm start`, with its environment from the unit's `EnvironmentFile`.
- Alternatives rejected: the `releases/<sha>` layout now (it is F3 and needs the unit and env work first); recording the app before building (a failed build leaves a unit-less entry); pulling an existing copy (could discard or clash with local edits).
- Consequences: no unit exists yet after install (next slice generates it from `run`, the env file and the absolute `node` path); the Pi's Node must already be installed (`install-node`) for apps that need it; the build runs with the Pi's user privileges, so only commands the developer wrote should go in `build`.

## 2026-11-15 — An app's repo, build and run commands are declared in the Pi's `apps.yaml`
- Decision: the app entry in `~/.raspi/apps.yaml` gets the optional fields `repo` (owner/name), `build` (commands run after checkout) and `run` (command the generated unit starts), later `port`. Clone and build (F10 steps 5-6) and unit generation (step 8) read them from there. Not built yet: schema, validation, wizard.
- Why: follows the 2026-11-14 decision that the Pi is the source of truth, so a reinstalled PC finds how each app is installed; no change needed in the projects themselves.
- Alternatives rejected: a `raspi.yaml` in each repo (every project to edit, and raspi must clone before it knows what to do); typing the commands at each install (nothing to replay on redeploy).
- Consequences: `parse_manifest`, `render_manifest` and `AppRef` grow these fields; the values are commands, so they are validated and shown in full before anything runs, never built by string concatenation.

## 2026-11-15 — Deploy keys: one read-only ed25519 key and one ssh alias per app, GitHub host keys from its API
- Decision: each app gets `~/.ssh/raspi_deploy_<app>` (ed25519, no passphrase, comment `raspi-<app>@<pi>`) created on the Pi, and a `Host github-<app>` block in `~/.ssh/config` (`HostName github.com`, `User git`, `IdentitiesOnly yes`, guarded by a marker comment so it is added once). The repo is cloned through that alias (`git@github-<app>:owner/name.git`). GitHub's host keys are put in `known_hosts` only when `github.com` is absent, taken from `https://api.github.com/meta` (`ssh_keys`, fetched by the PC over HTTPS, format-checked). The public key is shown for the developer to add as a read-only deploy key; `git ls-remote` (BatchMode, no prompt) verifies it. Existing keys and settings are never replaced.
- Why: a deploy key is tied to one repo, so one alias per app lets each repo use only its own key; no passphrase because deploys must run unattended; trusting GitHub's published keys avoids accepting a host key blindly on first use.
- Alternatives rejected: one shared key (GitHub refuses the same deploy key on two repos); `ssh-keyscan` (trust on first use); a key generated on the PC and copied (private key would travel); adding the key through the GitHub API (needs a token with admin rights on the repo, not wanted).
- Consequences: the key has no passphrase, so anyone with the Pi's login can read that repo (read-only); removing a key means deleting the two files and the config block by hand; not built: rotating a key.

## 2026-11-15 — Provisioning starts with `doctor` and a minimal `provision` (apt git/curl + `~/apps`)
- Decision: installs are triggered from raspi-manager in small slices, first the base of every Pi. `doctor` (read-only) lists the gaps; `provision` installs only `git` and `curl` through apt (a fixed whitelist, never a name from outside) and creates `~/apps`, after a confirmation showing the exact script. Node and uv are reported by `doctor` as optional gaps and not installed yet.
- Why: apt packages come from the distribution with its own signature checks, so this slice adds no third-party download. Node (nvm vs NodeSource vs the trixie package) and uv (installer script vs release binary) each need a method and a version policy, which is the developer's call.
- Node method chosen 2026-11-15: **nvm**, with the Node version picked per Pi or app (as on `raspi` today; units then use the absolute `node` path). Built the same day: nvm pinned to v0.41.0 (latest stable on GitHub, GPG-signed tag, checked online 2026-11-15); its install.sh is fetched from that tag and its SHA-256 (045932fe…f48b, computed from the tag's file) is checked on the Pi before it runs; offered Node lines 22, 24, 26 (LTS on nodejs.org the same day). The script runs without sudo and lets nvm edit the shell profile. Re-check the nvm tag and the LTS lines when touching this. uv: method still open.
- Alternatives rejected: the whole F10 wizard at once (too large to review); installing uv/Node with `curl | sh` without deciding (unpinned remote script run with the Pi's user).
- Consequences: a Pi without Node or uv is “ready” for apps that do not need them; the next slices are Node/uv, then the deploy key, clone and build, unit generation (F10 steps 4-8).

## 2026-11-14 — The Pi holds the app inventory (`~/.raspi/apps.yaml` on each Pi); the Pi is the source of truth
- Principle (reworded): the Pi describes and runs its apps; the PC is a control station that keeps only the address book (name, address, user in `hosts.yaml`) and credentials (SSH key, Cloudflare token in the Credential Manager). After a PC reinstall, re-adding the Pis must be enough to find the management state as it was left.
- Decision: each Pi carries `~/.raspi/apps.yaml` (user-writable, no sudo): `version: 1`, then per app name, systemd unit, repo folder, env files as label + path (never values), later port, deployed version, hostname. raspi-manager reads it from the Pi on every refresh, like live state; a missing file falls back to the apps in the PC `hosts.yaml`; an invalid file is ignored, shown in the status bar, and the fallback is used. Writes to the Pi file (add app, declare env file, publish) are atomic with a `.bak` on the Pi, previewed, confirmed, and run by the developer from the GUI. The `.env` file on the Pi is the reference for its variables; the local copy in `~/.raspi/env/` is a working draft.
- Clarification: Cloudflare is not on the Pi. Tunnels and routes live at Cloudflare and are read through the API each time; `apps.yaml` may name an app's public hostname but is not the truth for route state.
- Why: a reinstalled PC without `~/.raspi/` must not lose the management state; also resolves the BRIEF risk “`.env` files exist only on the PC”.
- Alternatives rejected: PC file stays the truth with a pushed backup copy (two sources to keep aligned, stale-copy risk).
- Consequences: not recovered by the Pi file alone: the list of Pis itself, the SSH key and host-key trust, the Cloudflare token and `~/.raspi/cloudflare.yaml` (ids can be looked up again from the token), local env drafts (re-importable from the Pi). Built so far: reading and validating `apps.yaml`, fallback, status bar note (slice 1); publishing the PC's apps to a Pi that has no `apps.yaml`, GUI and CLI, preview + confirmation + atomic write + `.bak` + read-back (slice 2; an existing Pi file is never replaced from the PC). Env file declarations are written where the app list lives: the Pi's apps.yaml when it has one (applied on the file read at that moment, atomic, `.bak`, read-back), hosts.yaml otherwise (slice 3). Whole apps are added by the adopt scan (read-only detection of the login user's services under /etc/systemd/system, explicit ticking, confirmed write; slice 4). Not built: removing a whole app or editing its fields, scan sources beyond systemd units. Until slice 3, “Declare an environment file” still edits the PC `hosts.yaml`, so it does not work for an app that only exists in a Pi's `apps.yaml`. `/etc/systemd/system/*.service` are not readable without sudo on `raspi`, so a scan reads units with `systemctl show`.

## 2026-11-14 — App routes: one connector unit per tunnel, token in a root-only env file
- Decision: “Set up route…” / `raspi route add` give each app its own tunnel (`raspi-manager-<pi>--<app>`) and install its connector on the Pi as `raspi-tunnel-<name>.service` (`ExecStart=<cloudflared> --no-autoupdate tunnel run`, `Type=simple`, `Restart=on-failure`) reading `TUNNEL_TOKEN` from `/etc/cloudflared/raspi-tunnel-<name>.env` (root, mode 600). `cloudflared` is installed only when missing, from the official GitHub release for `uname -m` (`arm`, `armhf`, `arm64`, `amd64`), after checking the SHA-256 published in the release notes; an existing install is reused as is. The plan is read-only, one confirmation shows every change and the exact Pi script with the token hidden; nothing runs on the Pi if its unit is already active. Verified online 2026-11-14: latest release 2026.11.0 (12 Nov 2026) with those four file names, checksums only in the release notes (`### SHA256 Checksums:`), token accepted by `tunnel run` through `--token` or `TUNNEL_TOKEN`, `--protocol auto` falls back from QUIC to HTTP/2 when UDP is blocked.
- Why: the official `cloudflared service install <token>` owns a single `cloudflared.service`, which cannot serve one tunnel per app on the same Pi, and it puts the token in the unit file where `systemctl status` and `ps` show it; the old `cloudflared.service` on `raspi` was in a restart loop for weeks (114k restarts, start timeout 15 s), so the new unit has no short start timeout.
- Alternatives rejected: `cloudflared service install` (single service, token visible); showing commands to paste in a terminal (token on screen and in shell history, chosen against by the developer); an apt install (needs repository setup, no checksum step of ours); a shared tunnel per Pi (the developer's per-project layout already exists in Add route…).
- Consequences: a Pi can run several tunnels; removing a connector is not built (disable and delete the unit and env file by hand); the token is readable only by root on the Pi and travels over ssh stdin; the checksum protects against a corrupted or truncated download, not against a compromised GitHub release since both come from GitHub. The port detection only sees processes of the login user (`ss -p`).

## 2026-10-17 — Environment editing: per-app `env_file`, PC copy + push, values never logged
